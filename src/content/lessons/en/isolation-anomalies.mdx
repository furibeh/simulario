<Stage stage="theory">

A **transaction** groups reads and writes. It ends in one of two ways:

- **`COMMIT`**: all its writes become permanent and visible at once.
- **`ROLLBACK`**: all its writes are discarded, as if they had never happened.

Until it commits, its writes are **uncommitted**.

A database serves many transactions at the same time and interleaves their operations, just as an operating system interleaves threads. Two rules decide what happens when they cross:

**Write locks.** At every level, a transaction that writes an item **locks** it until it commits or rolls back. If another one wants to write the same item, it **waits**. Reads, on the other hand, never wait.

**Isolation level.** It decides what a read sees while others are writing:

| Level | What a read sees |
| --- | --- |
| Read Uncommitted | The newest value, even if nobody has committed it. |
| Read Committed | Only committed values, plus the transaction's own writes. It is PostgreSQL's default. |

Many programs **read a value, compute in the application and write the result**: `SELECT balance`, then `UPDATE … SET balance = 150`. The database only sees the read and the write; the computation in between happens outside it.

> Example: a single transaction and `x = 100`. It reads 100 and writes 150. Until it commits, any other transaction in Read Committed still reads 100. Once it commits, they all read 150.

</Stage>

<Stage stage="explain">

The right answer was **120**. Two deposits were committed and only one survives: T1's 50 disappears.

**A transaction does not stop another one from overwriting your changes.** By turn 2, both have read 100. T1 writes 150 and commits. On turn 5, T2 writes the 120 it computed from that 100, unaware that `x` is already 150. When it commits, it erases T1's deposit. This is a **lost update**. If you said 170, you pictured each transaction working alone; if you said 150, you thought the first to commit wins.

**It is the same race as with threads, one level up.** Read, compute and write are the `load`, `add` and `store` of `counter++`. The difference is that what slips in between is not a thread switch but another transaction's commit.

**The write lock does not prevent it.** The lock only stops two **uncommitted** writes from overwriting each other (a *dirty write*, which no level allows). T1 releases the lock when it commits, before T2 writes. And if T2 tries to write earlier, it waits… but once it gets the lock it still writes its 120, computed from old data. You will see it in experiment 1.

**What each level forbids.** The SQL standard defines the levels by the anomalies they rule out. Read Uncommitted allows **dirty reads**: reading a value its writer can still roll back. Read Committed forbids them, but allows the lost update, **non-repeatable reads** (reading the same item twice and getting different values) and **read skew**: seeing one part of the data before a change and another part after it. Higher levels forbid these, and the next two modules show two ways to get there.

**A dirty read can see something that never existed.** If T1 writes 150 and then rolls back, a transaction in Read Uncommitted that read that 150 worked with a value the database never held. PostgreSQL accepts `READ UNCOMMITTED` but runs it as Read Committed; MySQL and SQL Server do allow dirty reads.

**Read Committed decides read by read.** A report that adds up two accounts while someone transfers money between them can read one before the transfer and the other after it, and add up money that was never there at the same time.

**You can fix it without changing the level:**

- **Let the database add**: `UPDATE accounts SET balance = balance + 20`. The second transaction waits for the lock and, once it has it, PostgreSQL re-reads the newest committed value before adding: 150 + 20 = 170. It is the atomic `inc` from the threads lesson.
- **Lock when reading**: `SELECT … FOR UPDATE` takes the write lock at the read, so T2's read waits until T1 commits and returns 150.
- **Raise the level**: under PostgreSQL's Repeatable Read, the second transaction aborts with a serialization error and has to be retried (module 7). With two-phase locking, reads take locks too (module 6).

**In real systems.** PostgreSQL and Oracle default to Read Committed; MySQL with InnoDB, to Repeatable Read. Many applications that use an ORM load an object, change a field and save it: exactly the *Balance* pattern.

</Stage>

<details>
<summary><strong>1.</strong> Make T2's write wait for T1's lock, and still lose T1's deposit.</summary>

In *Balance*, clear the order and choose T1, T2, T1, T2, T1, T2. On turn 4, T2 tries to write and waits because T1 holds the lock. When T1 commits, T2 gets the lock and writes the 120 it computed from 100. The result is still 120.

</details>

<details>
<summary><strong>2.</strong> Make T2 read a balance that never existed.</summary>

Choose *Dirty read* with Read Uncommitted. T2 reads the 150 that T1 wrote without committing, and then T1 rolls back: `x` was never 150. Switch to Read Committed and run it again: T2 reads 100.

</details>

<details>
<summary><strong>3.</strong> Make the report see more money than there is.</summary>

Choose *Transfer* with Read Committed. The report T1 reads `x = 50` before the transfer and `y = 90` after T2 commits: it adds up to 140, although the two accounts always hold 100 between them.

</details>

<details>
<summary><strong>4.</strong> Keep both deposits in <em>Balance</em> without changing the isolation level or the order of turns.</summary>

Under *How each deposit adds*, choose *The database adds* (`UPDATE x = x + 50`): T2 waits for the lock and adds 20 to the already committed 150. Or choose *Read with FOR UPDATE*: T2's read waits until T1 commits and returns 150. Either way, `x` ends at 170.

<Stage stage="deeper">

- **Phantoms.** A `WHERE` that, when repeated, finds a row another transaction inserted in between. Row locks do not prevent it; predicate or range locks do. This board works with individual items and does not simulate them.
- **Optimistic concurrency in the application.** A `version` column that the `UPDATE` checks in its `WHERE`: if someone changed it since you read it, the write matches no row and you know you have to retry.
- **Levels in between.** *Cursor Stability* and Oracle's *Read Consistency* sit between Read Committed and Repeatable Read.
- **More precise definitions.** Adya proposed defining isolation by cycles in a dependency graph (G0, G1, G2). Hermitage's test names come from there.
