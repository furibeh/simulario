<Stage stage="theory">

A **thread** is a sequence of instructions being executed inside a process. A process can have several threads, and they all **share** its memory (code, global variables, heap) and its open files. What each thread keeps **to itself** are its **registers**, its program counter and its stack.

The operating system schedules threads like it schedules processes: there is one CPU, one thread uses it at a time, and the timer can take it away when its **quantum** ends. In this lesson the quantum is counted in **instructions**.

A line like `counter++` on a global variable looks like one step, but the CPU runs three instructions:

| Instruction | What it does |
| --- | --- |
| `load` | `reg = counter`: copies the value from memory into one of the thread's registers. |
| `add` | `reg = reg + 1`: only the register changes; memory stays the same. |
| `store` | `counter = reg`: copies the register back to memory. |

When the system switches threads, it saves the registers of the outgoing thread and restores them when it comes back. Memory is not saved or restored: it is shared.

> Example: one thread and `counter = 5`. After `load`, the register holds 5. After `add`, the register holds 6 and `counter` is still 5. After `store`, `counter` is 6.

<Stage stage="explain">

The right answer was **1**. Two increments were requested and only one survives.

**`counter++` is not an indivisible step.** After instruction 2, T1 has 1 in its register but has not written it yet: `counter` is still 0. The timer interrupts it right there. T2 reads that 0, adds 1 and also ends up with 1. In the end both write 1. T2's store is **stale**: it computed it from a value that was no longer current, and it erases T1's increment.

**One CPU is enough.** The threads did not need to run at the same time on two cores. It was enough for the timer to cut T1 between its `load` and its `store`.

This is called a **race condition**: the result depends on the order in which the scheduler interleaves the threads. The piece of code that touches the shared data, here the three instructions from `load` to `store`, is a **critical section**. What we need is **mutual exclusion**: at most one thread inside the critical section at a time.

**Passing the tests proves nothing.** With quantum 3, each turn holds a whole `counter++` and the result is 2. But nothing in the code guarantees it: another thread, a page fault or an interrupt shifts the turns, and the race is back. That is why the result is called **indeterminate**: the same program, with the same input, gives 1 or 2.

**A longer quantum does not fix it.** On *Three threads* with quantum 4, the turns cut the second increment between `load` and `store`, and 2 out of 6 are lost. Fewer interruptions make the race rarer, not impossible.

**It can go very wrong.** On *Three threads* with quantum 2, six increments leave `counter` at 2. A single stale store can erase several increments at once: all the ones others made between its read and its write. With two threads doing *n* increments each (*n* ≥ 2), the result can drop to 2.

**What threads share.** T1's 1 was safe in its register while T2 ran, because each thread has its own registers and the system saves them on every switch. `counter`, on the other hand, exists once in memory. That is exactly why there is a race.

**The hardware's answer: atomic instructions.** Processors offer read-modify-write instructions that complete without another thread touching that memory in between: `lock xadd` on x86, `atomic_fetch_add` in C11, `std::atomic<int>::fetch_add` in C++, `AtomicInteger` in Java. With them `counter++` is a single indivisible operation, and no interleaving can split it. Critical sections longer than one instruction need locks, the topic of the next module.

**In real systems.** With several cores threads truly run in parallel and caches add surprises (memory reordering), but the lost update already appears with one core. In C and C++, two unsynchronized accesses to the same variable, at least one of them a write, are a *data race* and the behavior is undefined; tools like ThreadSanitizer detect them. In Python, `counter += 1` is several bytecode instructions and is not atomic either; the build without the GIL (officially supported since Python 3.14) only makes the race show up more often.

</Stage>

<details>

</details>

<details>

</details>

<details>
<summary><strong>4.</strong> Make every interleaving give the right answer.</summary>

Choose *Atomic*. `counter++` becomes a single indivisible instruction: there is no point where another thread can slip in between the read and the write.

<Stage stage="deeper">

- **Locks and semaphores.** To protect critical sections longer than one instruction, the next module builds mutual exclusion.
- **Memory reordering.** On multicore processors, one thread's writes can be seen in a different order from another core. The C11 and Java memory models say which orders are guaranteed.
- **Check-then-act.** `if (!exists(f)) create(f)` has a race even if each call is atomic: another thread can create the file between the check and the creation.
- **Race detectors.** ThreadSanitizer (`-fsanitize=thread` in GCC and Clang) watches memory accesses and reports the data races that happen during a run.
