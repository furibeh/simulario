<Stage stage="theory">

Two-phase locking makes readers and writers wait for each other. Almost every database today uses a different idea: **multiversion concurrency control** (MVCC).

- **Versions.** Writing an item does not erase the previous value: it adds a new **version**. Committed versions are kept as long as someone might need them.
- **Snapshot.** When a transaction starts (with its first operation), it takes a snapshot. All its reads see the versions **committed before that moment**, plus its own writes. Whatever others commit later is invisible to it.
- **Reading never waits**: a read just picks the version it is entitled to.
- **Writing still locks**: writing an item takes its exclusive lock, as in Read Committed. If another transaction changed that item and committed **after** your snapshot, your write would be based on a version you never saw: the database aborts you with a serialization error. This rule is called **first updater wins**.

This is what PostgreSQL runs when you ask for `REPEATABLE READ`.

> Example: `x = 100`. T1 starts and reads 100. T2 writes 150 and commits. If T1 reads `x` again, it still sees 100: the version in its snapshot.

</Stage>

<Stage stage="explain">

The answer was **0**: no doctor on call, and no error at any point.

**Snapshots are not serializable.** If you said one would stay, you thought one of them would see the other's change. In any serial order, the second doctor would see only one on call and stay. But both snapshots were taken before anyone wrote, so both checks see two on call. The snapshot rule only stops two transactions from writing **the same** item; here each wrote a different one, after reading the other's. This anomaly is called **write skew**.

**Checking the rule is not enough.** Each transaction, on its own, is correct: it checked the rule with the data it saw. Together they break it, because each decided with data the other was about to change.

**What snapshots do prevent:**

- **Dirty reads**: only committed versions are visible.
- **Non-repeatable reads and read skew**: every read uses the same snapshot. The report in *Transfer* sees 100 even though the transfer commits in the meantime (experiment 1).
- **Lost updates**: the first updater wins, and the second one is aborted (experiment 2).

**And they do it without making readers wait.** With two-phase locking, the transfer had to wait for the report. Here nobody waits: each one reads its own version.

**But it is not free.** Two writers of the same item still wait for each other, and when the first commits, the second is aborted. The application has to retry, just as with two-phase locking.

**How to prevent write skew:**

- **Two-phase locking**: the shared locks taken by the reads make the writes deadlock, and one transaction is aborted (experiment 3).
- **Make the conflict visible**: read the rows with `SELECT … FOR UPDATE`, so the second transaction waits and then fails, or have both write a common row.
- **Serializable Snapshot Isolation**, PostgreSQL's `SERIALIZABLE`: it keeps snapshot reads, but tracks the dependencies between what each transaction reads and what others write, and aborts one of a dangerous pair.

**In real systems.** PostgreSQL's `REPEATABLE READ` and Oracle's `SERIALIZABLE` are snapshot isolation. Old versions are cleaned up later (PostgreSQL's `VACUUM`), which is why a very long transaction keeps them alive and makes tables grow.

</Stage>

<Stage stage="deeper">

- **Where PostgreSQL keeps versions.** Every row carries `xmin` and `xmax`, the ids of the transaction that created it and of the one that deleted or replaced it. `VACUUM` reclaims versions nobody can see any more.
- **Serializable Snapshot Isolation.** It looks for the "dangerous structure": two consecutive read-to-write dependencies between concurrent transactions (Cahill et al., 2008; Ports and Grittner, 2012).
- **Per-statement snapshots.** PostgreSQL's and Oracle's Read Committed use versions too, but take a new snapshot for each statement.
- **Time travel.** Some databases let you read the data as it was in an old snapshot.

Further reading:

- Berenson et al., *A Critique of ANSI SQL Isolation Levels*, SIGMOD 1995, section 4.2. [Free at Microsoft Research](https://www.microsoft.com/en-us/research/publication/a-critique-of-ansi-sql-isolation-levels/).
- PostgreSQL documentation, *Repeatable Read Isolation Level* and *Serializable Isolation Level*. [postgresql.org](https://www.postgresql.org/docs/current/transaction-iso.html).
- Ports and Grittner, *Serializable Snapshot Isolation in PostgreSQL*, VLDB 2012.
