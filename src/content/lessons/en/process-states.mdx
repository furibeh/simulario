<Stage stage="theory">

A **process** is a program in execution. The operating system keeps a record of each one, the **process control block** (PCB), where it notes, among other things, which **state** the process is in.

A process alternates **CPU bursts**, when it computes, and **I/O bursts**, when it waits for a disk, the network or the keyboard. It always starts and ends with a CPU burst.

In this simulator there is one CPU, and only one process can use it at a time. Time advances in units and switching processes costs nothing. There are five states:

| State | What it means |
| --- | --- |
| **New** | Being created. Here it lasts zero time: an arriving process is admitted at once. |
| **Ready** | Could use the CPU right now and waits for its turn in the **ready queue**. |
| **Running** | Has the CPU. |
| **Blocked** | Waits for an I/O operation to finish. Giving it the CPU would be useless. |
| **Terminated** | Finished its last burst. |

The **scheduler** gives the CPU to the first process in the ready queue (first come, first served) whenever the CPU is free. I/O devices work in parallel with the CPU and with each other: here every process has its own device, so I/O never queues.

> Example: P1 arrives at 0 with CPU 1, I/O 2 and CPU 1, and it is alone. It runs from 0 to 1, is blocked from 1 to 3, becomes ready at t = 3 and immediately runs again until 4, when it exits. The CPU is idle from 1 to 3.

</Stage>

<Stage stage="explain">

The right answer was:

| Process | t = 3 | t = 5 |
| --- | --- | --- |
| P1 | Blocked | Ready |
| P2 | Running | Terminated |
| P3 | Ready | Running |

**The CPU does not wait for the disk.** At t = 2, P1 requests I/O and, in that same instant, leaves the CPU and becomes blocked. The scheduler dispatches P2 right away. If you put P1 as running at t = 3, you pictured the process keeping the CPU while it waits, or the CPU waiting for it. Neither happens.

**When its I/O finishes, a process goes back to the queue, not to the CPU.** At t = 5, P1's I/O ends, but it becomes ready and joins the queue behind P3, which has been waiting since t = 1. The scheduler picks P3. Even when the queue is empty, as it is for P3 at t = 8, the process passes through ready, just for zero time.

**There are six possible transitions**, and each one has a cause:

| Transition | Event | Who causes it |
| --- | --- | --- |
| New → ready | Admit | The operating system finishes creating the process. |
| Ready → running | Dispatch | The scheduler. |
| Running → blocked | I/O request | The process itself, through a system call. |
| Blocked → ready | I/O completion | An interrupt from the device. |
| Running → ready | Timeout | A timer interrupt. Only in preemptive systems. |
| Running → terminated | Exit | The process itself. |

No other transition is possible. A ready process cannot block, because it is not executing anything that could request I/O. A blocked process cannot run, because the scheduler only picks from the ready queue.

**Ready and blocked are not the same wait.** A ready process waits only for the CPU: if it got it, it would make progress. A blocked one waits for an event and would not use the CPU even if it had it.

**Multiprogramming.** On *Waiting for the disk* the CPU is busy all 9 units. Running the three processes one after another would take 2 + 3 + 2 + 3 + 1 + 2 + 1 = 14. The gain comes from overlapping one process's I/O with another's CPU burst. **CPU utilization** is the fraction of time the CPU is busy: busy units / total time.

**The PCB and the context switch.** On every dispatch the operating system saves the registers of the outgoing process in its PCB and loads the incoming one's. Here it is free; in a real system it takes a few microseconds.

**Real systems.** On Linux, `ps -o pid,stat,cmd` and `top` show each process's state. `R` means running or runnable (ready): Linux does not tell them apart. `S` and `D` are blocked (interruptible and uninterruptible sleep), `T` is stopped and `Z` is zombie: terminated, but not yet collected by its parent.

<Stage stage="deeper">

- **Suspended states.** When memory runs short, the system can move ready or blocked processes out to disk (swapping): this adds the ready-suspended and blocked-suspended states.
- **The long-term scheduler.** It can hold processes in the new state to cap how many compete at once, the **degree of multiprogramming**.
- **`fork()`, `exec()` and `wait()`.** On Unix a process creates another with `fork()`, replaces its program with `exec()` and waits for it to end with `wait()`. If the parent never calls `wait()`, the terminated child stays a zombie.
- **Devices with queues.** Here every process has its own device. If two processes need the same disk, the second one waits in the device's queue, not only for its own operation to finish.
