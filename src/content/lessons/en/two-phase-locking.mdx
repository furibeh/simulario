<Stage stage="theory">

In the previous lesson, only writes took locks. With **two-phase locking** (2PL), every access asks for a lock first:

- To **read** an item, a **shared** lock. Several transactions can share it.
- To **write** it, an **exclusive** lock. While someone holds it, nobody else can hold any lock on that item.
- A transaction that holds the shared lock and wants to write asks to **upgrade** it to exclusive, and for that every other reader has to be gone.

| Can it be granted? | Someone else holds shared | Someone else holds exclusive |
| --- | --- | --- |
| I ask for shared | Yes | No, I wait |
| I ask for exclusive | No, I wait | No, I wait |

The **strict** version, the usual one, keeps every lock until commit or rollback. The two phases are a **growing** phase, in which the transaction only takes locks, and a **shrinking** phase, in which it only releases them; the strict version releases them all at once, at the end.

If the waits form a **cycle**, the database **detects** it and **aborts** one transaction, the victim, so the others can go on. The application gets an error and has to retry it.

> Example: T1 reads `x` and takes a shared lock. T2 reads `x` too: now there are two readers. If T2 wants to write `x`, it needs the exclusive lock, but T1 is still reading: T2 waits until T1 commits.

<Stage stage="explain">

The answer was **the database aborts one of them**: T2. T1 commits and `x` ends at 150. Nothing is lost silently: the application knows T2 failed and can retry it; run again, T2 would read 150 and the total would be 170.

**One item is enough for a deadlock.** If you said both would wait forever, or that it takes two resources locked in opposite orders, you were thinking of the philosophers. Here each transaction holds a shared lock that the other needs gone before it can write. On turn 4 the cycle T2 → x → T1 → x → T2 closes.

**A database does not hang.** Unlike the operating system, which does not break deadlocks between an application's locks, the database looks for cycles and aborts a victim. PostgreSQL looks for them when a wait exceeds `deadlock_timeout` (1 s by default) and aborts the transaction that runs the check; MySQL with InnoDB detects them at once and aborts the one that has changed fewer rows. On this board the victim is always the one that closes the cycle.

**Why it is serializable.** Shared locks keep what a transaction read from changing until it ends, and exclusive locks keep others from seeing what it wrote. So every conflict between two committed transactions goes the same way, and the result is the same as running them one after another, in the order they committed (Eswaran et al., 1976).

**Write locks were not enough.** If you said a deposit would be lost, you were thinking of Read Committed, which also locks when writing. What it lacked was locking when reading: T2 could write from a value T1 had already changed. Under 2PL, T2's shared lock forbids that change while T2 is alive.

**What became of the previous module's anomalies.** The lost update turns into a deadlock and an abort, as you just saw. The read skew of *Transfer* turns into a wait: the transfer cannot write `x` while the report is reading it (experiment 1).

**The price:**

- **Readers block writers**, and writers block readers.
- **Upgrading a shared lock to exclusive** causes deadlocks even with a single item.
- **You have to retry**: an application that uses this level must catch deadlock or serialization errors and run the transaction again.

**Avoiding the upgrade deadlock.** Reading with `SELECT … FOR UPDATE` takes the exclusive lock from the start: the second transaction waits at its read instead of deadlocking at its write (experiment 2).

**Who uses it.** SQL Server and MySQL with InnoDB implement Serializable with locks like these; InnoDB turns every `SELECT` into a read with a shared lock. PostgreSQL's Serializable uses a different technique, *Serializable Snapshot Isolation*, built on the versions of the next module.

</Stage>

<Stage stage="deeper">

- **Granularity and intention locks.** A database can lock a row, a page or a whole table. Intention locks (IS, IX) let them coexist.
- **Predicate and range locks.** They prevent the phantoms of the previous lesson.
- **Preventing instead of detecting.** *Wait-die* and *wound-wait* use the age of transactions to decide who waits and who aborts, so a cycle never forms.
- **Serializable Snapshot Isolation.** PostgreSQL's Serializable detects dangerous structures between transactions instead of locking reads (Cahill et al., 2008).
